## 2. 表情增强实施方案（重点）

### 2.1 表情的真实数据链路

TTSA 侧的表情**不是**一个可以远程调用的"setEmotion"接口，而是一条自动链路：

```
send_text(is_start 首段)
    ├─ extra.emotion / emotion_scale / context_texts  ← 应用层可覆盖（单轮）
    ↓
tts_config.support_emotion（会话级白名单）  ← 决定分句服务是否做情感识别
    ↓
分句服务（gRPC intent_predict）返回 res.sentimental（新版）/ res.emotion（旧版）
    ↓
face_ka_v2 / face_ka 事件（内部 TOPICS.FACE_KA_DATA）
    ↓
AI Render 生成面部数据 → face_data（PCA 权重，24FPS）→ SDK 渲染
```

**三条可操作的控制点**：

| 控制点 | 层级 | 作用范围 | 应用层能否操作 |
|---|---|---|---|
| `tts_config.support_emotion` | 会话级 | 决定情感识别**是否启用**、识别哪些标签 | ⚠️ 属会话 TTS 配置，**需确认部署环境是否开放**（见 §2.2） |
| `send_text.extra.emotion` / `emotion_scale` / `context_texts` | 单轮 | 覆盖本轮情感与强度 | ✅ 可通过 SDK `speak(ssml, is_start, is_end, extra)` 传入 |
| SSML `<ue4event><type>ka</type>` | 单条发言内 | 触发具体关键动作（点头、招手…） | ✅ 可写入文本流 |

> ⚠️ **重要约束（来自后端代码）**：`emotion` / `context_texts` / `emotion_scale` **只有 `is_start=true` 的那一段生效**，后续段携带会被忽略。因此流式播报时，情绪必须在**每轮的首帧**决定 —— 这直接影响架构设计（见 §2.4）。

### 2.2 前置条件：会话级开关（必须先验证）

官方 `config` 参数表（`avatar-works/.claude/knowledge/sdk-api.md:41-80`）明确列出了可下发的会话配置，这**修正了上一版"表情配置客户端不可控"的悲观判断**：

| 项 | 目标值 | 下发位置 | 可行性 |
|---|---|---|---|
| `auto_ka` | `true`（启用自动 KA 动作） | `config.auto_ka` | ✅ 官方 config 参数表内 |
| `sta_face_id` | 目标面部模型 ID | `config.sta_face_id` | ✅ 同上 |
| `look_name` | 角色形象 ID | `config.look_name` | ✅ 同上 |
| `mp_service_id` | 动作库服务 ID | `config.mp_service_id` | ✅ 同上 |
| `tts_vcn_id` | 音色 ID | `config.tts_vcn_id` | ✅ 同上 |
| `lite_drive_style` | 驱动风格（如 `lively`） | `config.lite_drive_style` | ✅ 同上 |
| `tts_config.support_emotion` | 情感白名单 | 完整版 SDK 的会话顶层字段 | ⚠️ 待验证（Q1） |

**当前代码缺口**：`digitalAvatarProvider.ts:72-84` 的 `config` **只放了 `init_events`**，上述可下发项全部未使用。

**执行动作（M2 前置任务）**：

1. 在 `agentOptions.config` 中补齐 `auto_ka: true` 及角色相关 ID，重跑并检查 TTSA 日志是否出现 `IntentGenerator(..., auto_ka=True)`。
2. 抓取一次真实会话的 `start_session` 请求/响应，确认返回的 `config` 中是否含 `tts_config`、`support_emotion`。
3. 用一段明确带情绪的文本（如"太好了，这个方案非常棒！"）测试，观察 `face_data` 是否随文本变化（对比中性文本）。
4. 若 `support_emotion` 确实不可控 → 走**降级方案**：仅靠 `auto_ka` + 显式 KA 动作表达态度，并在文档中如实说明该限制。

> **KA 动作名必须从动作库确认**：官方示例给出 `RightSide02`（`sdk-api.md:145`），但可用清单未知。动作名不存在时后端返回 `deleted=true, deleted_reason="ka not found"`。`ka_intent` 可用语义名（官方示例 `<name>greeting</name>`）。

### 2.3 单轮情绪覆盖（代码级）

**当前代码**（`digitalAvatarProvider.ts:154-185`）：`speakChunk` / `endSpeakStream` 手工 `sendControl`，**未传 `extra`**，因此情绪覆盖能力被浪费。

**改造**：给 `AvatarProvider` 接口增加 `extra` 透传。

```ts
// src/providers/avatarProvider.ts
export interface SpeakExtra {
  emotion?: string          // 覆盖本轮情感，需在 support_emotion 白名单内
  emotion_scale?: number    // HSPro2 情感强度
  context_texts?: string[]  // HSPro2 语气参考文本
  client_speak_id?: string  // 用于把回调与请求关联
}

speakChunk?(text: string, extra?: SpeakExtra): void
endSpeakStream?(text: string, extra?: SpeakExtra): void
```

```ts
// src/providers/digitalAvatarProvider.ts
speakChunk(text: string, extra?: SpeakExtra): void {
  if (!this.agent || !text.trim()) return
  const isStart = !this.speakStreamStarted
  this.speakStreamStarted = true
  ;(this.agent as any).sendControl({
    type: 'speak',
    // 关键：仅首段携带 extra（后端只读 is_start 段）
    message: { text, is_start: isStart, is_end: false, ...(isStart && extra ? { extra } : {}) },
  })
}
```

> ⚠️ **必须遵守**：同一轮分段的 `extra` 应保持一致；且只有 `is_start` 段的 `extra` 有意义。这是后端明确写在文档里的行为，不要逐段重复传 `emotion` 并期望生效。

### 2.4 情绪决策：`set_emotion` 工具

情绪来源 = LLM 决策（而不是前端硬编码）。把它做成 Function Calling 工具：

```python
# server/services/interview_tools.py
{
  "type": "function",
  "function": {
    "name": "set_emotion",
    "description": "设置面试官本轮发言的情绪与关键动作，用于表达对候选人回答的态度",
    "parameters": {
      "type": "object",
      "properties": {
        "emotion": {"type": "string", "description": "情绪标签，必须来自已确认的 support_emotion 白名单"},
        "emotion_scale": {"type": "number"},
        "ka": {"type": "string", "description": "关键动作 action_semantic，如点头/思考类动作"},
        "reason": {"type": "string", "description": "选择该情绪的内部判断依据"}
      },
      "required": ["emotion"]
    }
  }
}
```

工具的产出**同时喂给两个通道**：

| 通道 | 载体 | 效果 |
|---|---|---|
| 嘴与脸 | 写入本轮 `speak` 的 `extra.emotion` | 语气 + 表情（face_ka_v2） |
| 身体 | 在文本中插入 `<ue4event><type>ka</type><data><action_semantic>…</action_semantic></data></ue4event>` | 关键动作 |

**面试情绪映射表（emotion 标签必须实测确认；KA 动作名必须从动作库穷举）**：

| 面试情境 | emotion（候选） | KA 动作（候选，示例） |
|---|---|---|
| 开场问候 | `happy` | `<type>ka_intent</type><data><name>greeting</name></data>` |
| 回答优秀 | `happy` | 点头类 ka（`action_semantic`） |
| 回答含糊 | 中性或疑惑类 | 思考类 ka（`action_semantic`） |
| 严重跑题 | 严肃类 | `<action_semantic>RightSide02</action_semantic>`（官方示例动作） |
| 时间告急 | 中性 | 提示类 ka |
| 结束致谢 | `happy` | `<type>ka_intent</type><data><name>ThankYou</name></data>` |

**SSML 写法（严格按官方语法，勿自创）**：

```xml
<speak>
  我们先聊到这里，
  <ue4event>
    <type>ka</type>
    <data><action_semantic>RightSide02</action_semantic></data>
  </ue4event>
  我看你时间也不多了。
</speak>
```

> **动作名不是随便起的**：KA 不存在于动作库时，后端返回 `deleted=true, deleted_reason="ka not found"`（`api_socketio_events.md:581`）。因此**动作名清单必须在 M2 阶段从动作库穷举确认**，并把结果写回本表。写作时注意 `<type>ka</type>` 用 `<action_semantic>`，而 `<type>ka_intent</type>` 用 `<name>` —— 两者字段不同，不要混用。

### 2.5 架构影响：情绪必须在"首帧"确定

因为 `extra` 只在 `is_start` 段生效，流式播报存在一个时序矛盾：

```
LLM 流式输出 token ──► 我们想边生成边播 ──► 但情绪要在首帧就定
```

**解决方案（二选一，推荐 A）**：

- **方案 A（推荐）**：让 LLM 在每轮回复的**开头**先吐一个结构化标记（或先走一次 `set_emotion` 工具调用），拿到情绪后再开始流式播报正文。代价是首字延迟略增（一次工具调用的往返），收益是表情与内容语义真正对齐。
- **方案 B**：用"上一轮对话质量"预测情绪，作为首帧的默认情绪，正文流式不受影响；本轮结束时再用 `set_emotion` 修正下一轮。代价是表情滞后一轮。

**决策依据**：方案 A 更符合"情绪跟随语义"这一核心卖点（也是消融实验里的关键变量），建议 A 为主、B 作为工具超时时的兜底。

### 2.6 表情验证步骤与判定标准

| 步骤 | 操作 | 判定标准 |
|---|---|---|
| V1 | 中性文本 vs 明显情绪文本各播一次，抓 `face_data` | 两者 PCA 权重序列存在可观测差异 |
| V2 | 同一文本，`extra.emotion` 分别传两个不同白名单标签 | 表情有差异，且不同于不传 |
| V3 | 传白名单外的标签 | 确认后端行为（忽略 / 报错），据此决定前端是否做白名单校验 |
| V4 | 在文本中插入 `<ue4event ka>` | 收到 `ka` 事件且 `deleted=false`，身体有对应动作 |

## 3. Widget 增强实施方案（重点）

### 3.1 Widget 的两条通道

| | 通道 A：服务端 `uievent` | 通道 B：客户端 `proxyWidget` / `onWidgetEvent` |
|---|---|---|
| 触发 | 文本流中的 `<uievent>` 标签 | 前端收到业务事件后自行渲染 |
| 同步 | **帧级同步**（`start_frame`/`end_frame`，与语音严格对齐） | 由业务事件驱动，无帧对齐 |
| 可控性 | 依赖文本穿透 E2E Server → TTSA | **100% 可控**，纯前端 |
| 适用 | "说到哪弹哪"的媒体（图片/视频/轮播） | 复杂交互（雷达图/表格/代码/判题卡） |
| 风险 | Agent 模式下文本经 E2E Server 转发，**是否原样透传未经证实** | 无 |

**结论**：**通道 B 做主力**（功能全、可控、零风险），**通道 A 做差异化增强**（帧级同步是"具身"的加分项，但需先验证穿透性）。

#### ⚠️ 类型命名存在两套，必须先探测

| 来源 | 类型命名 |
|---|---|
| TTSA 服务端协议（`ttsa_backend_lite/docs`） | `widget_pic` / `widget_text` / `widget_image` / `widget_video` / `widget_slideshow` / `widget_webpage` / `widget_close` |
| litesdk 官方文档与模板 | `show_image` / `show_video` / `show_link` / `show_model3d` / `show_text` / `bgm_start` |

官方模板 `useCustomWidget.ts:104-111` **同时注册了 `show_text` 与 `widget_text`** —— 证明实践中两套命名都会出现（取决于后端/版本）。

**因此第一步不是写代码，而是探测**（见 §3.6 W0）。

### 3.2 通道 B：客户端接管（推荐主力方案）

SDK 的 widget 分发逻辑（`UIRenderer.ts:144-164`）是明确的扩展点：

```
遍历 event.e 中的 widget 事件
  ├─ 有 CUSTOM_WIDGET（即 onWidgetEvent）→ 全部交给它，从待处理列表移除
  ├─ 否则查 PROXY_WIDGET[widgetData.type] → 命中则调用，从待处理列表移除
  └─ 剩余 → 内置 TrackerRenderer（仅 widget_pic / subtitle_on / subtitle_off）
```

**关键实现事实**：
1. `proxyWidget` 是 `{ [type: string]: (data) => void }`，**按 `widgetData.type` 精确匹配**——不是只有 subtitle 两个 key，可以是任意 widget 类型。
2. `onWidgetEvent`（= `CUSTOM_WIDGET`）优先级更高，一旦提供就**全量接管**，此时 `proxyWidget` 不再被调用。
3. `widgetData` 结构为 `IRawWidgetData { type, data, text, speech_id, client_speak_id }`。
4. SDK 内置**只实现了图片与字幕**；`widget_text` / `widget_video` / `widget_slideshow` 服务端会下发但客户端默认**不渲染**——所以想用这些类型，**必须**自己接管。

**改造 `digitalAvatarProvider.ts`**：

```ts
// 新增 widget 回调注册
private widgetCallback: ((w: RawWidgetData) => void) | null = null

setOnWidget(cb: (w: RawWidgetData) => void): void {
  this.widgetCallback = cb
}

// 在 agentOptions 中补齐 proxyWidget 的类型
// 注意：以下两套命名都注册（W0 探测后可精简为本项目实际使用的那一套）
"proxyWidget": {
  subtitle_on:  (d: any) => this.subtitleCallback?.(d?.data?.text ?? d?.text ?? null, true),
  subtitle_off: (_: any) => this.subtitleCallback?.(null, false),

  // TTSA 命名（SDK 内置仅实现 widget_pic，其余必须由业务侧接管）
  widget_pic:       (d: any) => this.widgetCallback?.({ type: 'widget_pic', ...d }),
  widget_image:     (d: any) => this.widgetCallback?.({ type: 'widget_image', ...d }),
  widget_text:      (d: any) => this.widgetCallback?.({ type: 'widget_text', ...d }),
  widget_video:     (d: any) => this.widgetCallback?.({ type: 'widget_video', ...d }),
  widget_slideshow: (d: any) => this.widgetCallback?.({ type: 'widget_slideshow', ...d }),
  widget_webpage:   (d: any) => this.widgetCallback?.({ type: 'widget_webpage', ...d }),
  widget_close:     (d: any) => this.widgetCallback?.({ type: 'widget_close', ...d }),

  // litesdk 命名（官方文档与模板使用）
  show_image:    (d: any) => this.widgetCallback?.({ type: 'show_image', ...d }),
  show_video:    (d: any) => this.widgetCallback?.({ type: 'show_video', ...d }),
  show_link:     (d: any) => this.widgetCallback?.({ type: 'show_link', ...d }),
  show_model3d:  (d: any) => this.widgetCallback?.({ type: 'show_model3d', ...d }),
  show_text:     (d: any) => this.widgetCallback?.({ type: 'show_text', ...d }),
  bgm_start:     (d: any) => this.widgetCallback?.({ type: 'bgm_start', ...d }),
}
```

> **取值路径注意**：官方模板用 `data?.data?.<field>` 取值（如 `data.data.image`），`widget_text` 则兼容 `data?.data?.text_content ?? data?.text_content`。字幕官方写法是 `d?.data?.text ?? d?.text`（`useCustomWidget.ts:88-111`）。现有项目代码只读了 `d?.text`，**可能读不到字幕**——这本身就是个待修的点。

> ⚠️ **不要启用 `onWidgetEvent`——理由比"优先级覆盖"严重得多**：
> 官方陷阱清单明确记载（`pitfalls.md:47-54`）：设置 `onWidgetEvent` 后 SDK 进入 CUSTOM_WIDGET 模式，**内部所有 UI 渲染被禁用，包括行走的 canvas 偏移** → 数字人**原地踏步不会移动**。
> 对面试场景这是致命的（§5 的"走向白板"依赖行走）。而官方示例中 `agent-dev.md:127` 建议用 `onWidgetEvent` 接管字幕 —— 该建议与 pitfalls 冲突，我们**采信 pitfalls**（来自真实事故）。
> 结论：**用 `proxyWidget` 覆盖全部类型，不用 `onWidgetEvent`。** 字幕继续走 `proxyWidget.subtitle_on/off`，行走由 SDK 默认逻辑处理。

### 3.3 通道 A：服务端 uievent（帧级同步增强）

**协议（来自 `api_socketio_events.md` 附录）**：

```xml

| type | 字段 |
|---|---|

<!-- 视频 -->
<uievent><type>show_video</type><data><video>URL</video><cover>封面URL</cover><title>标题</title></data></uievent>

<uievent><type>show_model3d</type><data><model_url>URL</model_url><title>标题</title></data></uievent>

<uievent><type>show_text</type><data><title>标题</title><text_content>内容</text_content></data></uievent>

```

**`axis_id` 的真实语义（易踩坑）**：SDK 直接把它当作 **CSS `z-index`**（`render-implements.ts:100`），同时 `x_location`/`y_location`/`width`/`height` 是 **0~1 的比例**（`top: y*100%`）。因此 `axis_id` 应当规划为**固定层级表**，而不是随意的随机数：

| axis_id | 用途 | 说明 |
|---|---|---|
| 100 | 数字人画布锚点 | 已由 `init_events` 的 `SetCharacterCanvasAnchor` 占用（现有配置） |
| 900 | 数据面板层 | 雷达图/匹配表 |
| 950 | 卡片层 | 题目卡/报告卡 |
| 1000 | 字幕层 | SDK 内置字幕默认 1000（`TrackRenderer/index.ts:25`） |
| 1100 | 模态层 | 需要压在字幕之上时使用 |

**落地方式**：在 brain 生成的文本中插入标签，**口播文本必须在标签外**。

```xml
<speak>
  你的简历里有一段电商项目经历，
  <uievent><type>show_text</type><data><title>项目经历</title><text_content>订单模块 · 日均 200 万单</text_content></data></uievent>
  我们重点聊聊订单模块的幂等设计。
</speak>
```

> ⚠️ **官方陷阱（`pitfalls.md:56-75`）**：`<uievent>` 标签**内**的文本**不会被口播**。若把要讲的话写在标签里，数字人会把整段内容念成标签文本（或静默跳过）。口播内容必须放在标签**外**，标签只承载控件数据。

> ⚠️ **未验证风险**：Agent 模式下文本先到 E2E Server 再转 TTSA，`<uievent>` / `<ue4event>` 是否原样透传**未经证实**。这是 M4 的第一个验证任务（§3.6 W0/W1）：
> 1. 直接调 `agent.speak(ssmlWithUievent)`（SDK 源码确认 `speak` 第一参数即 SSML，直发 TTSA）；
> 2. 若通，再验证 brain 输出文本中携带标签的路径；
> 3. 若不通，通道 A 降级为"仅通过 `speak` 直发"，或完全走通道 B。
> 官方 `useSDK.ts:111-122` 用正则从 SSML 中提取 `<target>` / `<action_semantic>` / `<type>` 做日志 —— 可作为我们的探测手法参考。

### 4.3 流式工具循环

```python
for round in range(MAX_ROUNDS):            # MAX_ROUNDS = 3
    content_buf, tool_calls = "", {}
    async for chunk in await client.chat.completions.create(
        model=cfg.model, messages=messages, tools=TOOL_SCHEMAS, stream=True
    ):
        d = chunk.choices[0].delta
        if d.content:

            yield sse(d.content)            # 直接吐给 SDK → 数字人开口
        if d.tool_calls:                    # ⚠️ 流式下是分片，需按 index 拼接 name/arguments

    for tc in tool_calls.values():

        if result["widget"]:
            publish(interview_id, {"type": "widget", "payload": result["widget"]})
        messages += [assistant_tool_msg(tc), tool_msg(tc.id, result["speak"])]
```

**实现要点**（项目历史踩坑，必须遵守）：
- 流式 `tool_calls` 分片需按 `index` 累积 `function.arguments` 字符串后再 `json.loads`
- 每轮必须 `await`（漏 await 会导致 `async for` 协程报错）
- 数据库操作使用独立 `Session(engine)`（流式期间注入的 session 会被关闭）
- `finally` 中确保发送 `finish_reason` chunk 与 `[DONE]`

### 4.4 事件总线（通道 B 的数据源）

新增 `server/services/interview_event_bus.py`（`publish` / `subscribe`，`dict[int, set[asyncio.Queue]]`），路由 `GET /api/interview/{id}/events`（SSE，沿用 `X-Accel-Buffering: no`）。

### 4.5 SSE 旁路事件类型

| 事件 | 载荷 | 前端动作 |
|---|---|---|
| `tool_start` | `{name}` | 可选：显示"正在查阅…" |
| `tool_result` | `{name, ok, ms}` | 埋点 |
| `widget` | `WidgetPayload` | 推入 Widget 栈 |
| `emotion` | `{emotion, ka}` | 写入下一轮首帧 `extra` + 插入 KA 标签 |
| `metrics` | `{ttfa, toolMs, interruptMs}` | 延迟面板 |

## 5. 具身状态机与播报管线

### 5.1 具身状态绑定

SDK 已原生暴露状态接口（`index.ts:1367-1395`、官方 `sdk-api.md:128-154`），直接绑定即可，**无需 hack**：

| 面试阶段 | 调用 | 说明 |
|---|---|---|
| 等待候选人开口 | `listen()` | 配合 `startASR()` |
| 候选人答完、LLM 生成中 | `think()` | **正好覆盖 LLM 首 token 前的空窗**，观感提升最明显 |
| 数字人发言 | `speak()` | 自动 |
| 等待候选人写代码 | `interactiveidle()` | |
| 面试结束 | `idle()` | |

现有 `digitalAvatarProvider.ts` 未暴露这些方法 → **接口需补齐**：`listen()` / `think()` / `interactiveIdle()`。

### 5.2 分句与播报队列（必须按官方范式实现）

**分句规则（官方 `llm-stream-pattern.md:89-137`）**：

```ts
const SENTENCE_END = /[。？！；\n]/     // 句末标点
const MIN_FIRST_SENTENCE = 20           // 首句最少 20 字
```

**为什么首句要 20 字**：LLM 开头常是"好的""没问题"这类短礼貌语，若 2-3 字就播报，数字人会**"抽搐式"说话**。攒够 20 字再切第一句，体验自然得多。

**播报必须用队列串行**（官方 `llm-stream-pattern.md:193-222`）：LLM 流式输出快、`speak()` 受 TTS 合成速度限制，**连续调用 `speak()` 会导致后者覆盖前者、TTS 混乱**。用队列 + `onSpeakStateChange('end')` 触发下一句（`drainQueue`）。

> 这与现有 `digitalAvatarProvider.speakChunk()` 的做法需要对齐：当前是直接 `sendControl` 分帧，未做队列背压。改造时要注意 §2.3 的 `extra` 只挂在首帧，与队列结合时别把首帧标记搞乱。

### 5.3 行走（walk）与 `walk_points`

行走可用于"面试官走到白板前讲算法题"，是具身感的加分项。官方语法：

```xml
<ue4event><type>walk</type><data><target>K</target></data></ue4event>
```

**⚠️ 必须避开的坑**：
1. **`walk_points` 的 key 是 F~U**，A~E 为 SDK 内部预留，用了不生效（`pitfalls.md:15-25`）。当前若按 A/B/C 配置行走，**不会生效**。
2. **不能启用 `onWidgetEvent`**，否则行走偏移失效、数字人原地踏步（§3.2）。
3. 行走属于定制化角色能力，需角色制作时预置行走动画；未配置时降级为原地动作。

### 5.4 打断：六项同步清理

`enableClientInterrupt` 在 Agent 模式已默认 `true`（`agent/index.ts:195`），但现有 `InterviewView.vue:285` 的 `handleInterrupt()` 只做了端侧停止。按官方清理清单（`llm-stream-pattern.md:226-243`）补齐：

| # | 清理项 | 现状 |
|---|---|---|
| 1 | 端侧：`interrupt('user')` → 立即停嘴 | ✅ 已有 |
| 2 | 播报队列 `speakQueue.length = 0` | ❌ 缺（引入队列后才有） |
| 3 | `isSpeaking = false` 重置 | ❌ 缺 |
| 4 | LLM 流 `AbortController.abort()` | ❌ 缺 |
| 5 | `isFirstSentence = true` / buffer / 字数 重置 | ❌ 缺 |
| 6 | 上下文：把**已播报出的部分**写入面试记录 | ❌ 缺（否则多轮记忆错乱） |

> 官方强调：`interrupt()` 是**异步**的（等待 SDK 停止当前播报），必须 `await` 后再发新的 `speak()`，不要用同步打断。

### 5.5 面试流程状态机（借鉴官方业务流范式）

官方业务模板把流程抽象为状态机（`business-flow.md`、`state-machine.ts`），**面试天然适配**：

```ts
interface InterviewStateDef {
  layout: 'half_center' | 'pip'
  widgetType: 'picker' | 'input' | 'text' | 'confirm'
            | 'question_card' | 'judge_result' | 'match_score' | null
  subtitleText: string        // 数字人引导语
  progressIdx: number         // 进度条位置，-1 隐藏
  inputMode: 'llm' | 'regex' | 'passthrough' | 'none'
  llmIntents?: string[]       // 白名单，防 LLM 乱跳
  nextState?: string | null
  retry?: { maxRetries: number; onFail: string; errorMsg: string }
}
```

面试状态表（草案）：

| 状态 | layout | widget | inputMode | 说明 |
|---|---|---|---|---|
| `opening` | half_center | `picker` | none | 开场 + 候选人选择面试方向 |
| `ask` | half_center | null | llm | 正常提问，LLM 决定追问或换题 |
| `followup` | half_center | null | llm | 追问（受 `followupLevel ≤ 2` 约束） |
| `algorithm` | half_center | `question_card` | passthrough | 出算法题 + 代码面板 |
| `judge` | half_center | `judge_result` | llm | 判题结果 + 讲解 |
| `closing` | pip | `text` | llm | 小结，数字人让位 |
| `report` | pip | `text` + actions | none | 报告 + 跳转完整报告 |

**可直接复用的两点**：
1. **Widget 点选自带 `intent` → 直接跳状态，不走 LLM**（如候选人点"跳过此题"）
2. **`llmIntents` 白名单**防止 LLM 乱换状态 —— 映射到面试就是"防止面试官乱跳题"，对评分一致性有帮助
3. **`retry` 机制**：候选人连续答不上来时（`maxRetries`），自动降级到换个话题，而不是死磕

### 5.6 销毁顺序（强制）

官方陷阱（`pitfalls.md:5-13`）：销毁顺序不可颠倒。

```ts
sdk.interrupt('user')   // 1. 先打断
sdk.offlineMode()       // 2. 再下线
sdk.destroy()           // 3. 最后销毁
```

现有 `digitalAvatarProvider.destroy()` 直接调 `agent.destroy()` → **需按上述顺序补齐**，否则资源未释放或报错。

## 6. 容错与降级

| 风险 | 措施 |
|---|---|
| 表情链路不可用（`support_emotion` 未开放） | 降级为 KA 动作表达态度（§2.2 第 4 步），并如实写入文档 |
| `uievent` 标签不透传 | 通道 A 降级；Widget 全走通道 B（功能不减少，仅失去帧级同步） |
| **Widget 类型名不确定（`show_*` vs `widget_*`）** | M4 先做 W0 探测，据实刻定 `proxyWidget` 的 key |
| KA 动作名不存在 | 后端会 `deleted=true`；前端不依赖 KA 成功，仅作增强 |
| 工具超时（Judge0 慢） | 过场语掩盖 + 超时阈值；超时则 `ok=false` 让 LLM 用话术兜底 |
| 工具调用死循环 | `max_rounds=3` |
| `session_speak_req_id` 跳号 | 流式分段必须从 0 连续递增（否则永久堵塞） |
| 断线 | SDK 自动重连 + `retransmit` 补发 5 秒；事件总线断线重订阅 |
| WebGL 上下文丢失 | SDK 自愈；初始化失败回落 Lottie（已有逻辑） |
| 积分不足 | 演示路径固定、减少冗余 LLM 调用；备录屏 |

### 6.1 官方常见故障速查（直接对照排查）

来自 `agent-dev.md:150-160` 与 `pitfalls.md`：

| 现象 | 原因 | 解决 |
|---|---|---|
| 数字人不说话 | SSML 没包 `<speak>` 标签 | `sdk.speak('<speak>…</speak>', isStart, isEnd)` |
| 字幕不更新 | 没订阅字幕事件 | 用 `proxyWidget.subtitle_on/subtitle_off`（**注意是两个独立事件**） |
| 数字人原地踏步 | 误启 `onWidgetEvent` 禁用了行走偏移 | 改用 `proxyWidget` |
| 行走不生效 | `walk_points` 用了 A~E | 改用 F~U |
| 初始化报 TypeError | 缺必填参数 | `containerId` 带 `#`、`config` 含 `layout`+`walk_config`、必填回调全传 |
| 网页有啸叫 | 音频管线未正确连接 | `ScriptProcessorNode` 必须双向连接，`gain=0` 静音 |
| 销毁报错 | 顺序错误 | `interrupt` → `offlineMode` → `destroy` |

### 6.2 错误码分级（用于延迟面板与降级判定）

官方错误码分段（`reference/sdk-api.md:249-293`），可作为我们前端错误处理的分类依据：

| 段 | 类别 | 典型码 |
|---|---|---|
| 10001-10004 | 初始化 | `CONTAINER_NOT_FOUND` / `CONNECT_SOCKET_ERROR` / `START_SESSION_ERROR` |
| 20001-20006 | 前端处理 | `FACE_PROCESSING_ERROR` / `RENDER_FACE_ERROR` |
| 30001-30005 | 资源管理 | `BACKGROUND_IMAGE_LOAD_ERROR` / `FACE_BIN_LOAD_ERROR` |
| 40001-40007 | 数据解压 | `AUDIO_DECODE_ERROR` / `TTSA_ERROR` |
| 50001-50004 | 网络 | `NETWORK_DOWN` / `NETWORK_RETRY` / `NETWORK_BREAK` |

面试页面可据此在顶部提示条给出可读文案（如 `NETWORK_BREAK` → "网络已断开，正在重连"）。

## 7. 演示脚本（3~5 分钟）

1. **开场（20s）**：数字人**微笑致意**（emotion）→ 展示 Listen/Think/Speak 状态指示器
2. **简历驱动提问（60s）**：说"我先看一下你的简历"→ `think()` → 弹 `ResumeHighlightWidget` → 针对项目提问
3. **打断（40s）**：候选人中途打断 → 数字人立即停嘴转聆听（**现场展示打断延迟**）
4. **算法题（60s）**：数字人**走到白板前**（walk）→ 出题 → `QuestionCardWidget` → 写码 → `run_code` → `JudgeResultWidget`
5. **情绪变化（30s）**：故意答错 → 面试官**表情转为严肃 + 抬手示意**（现场对比"答对时的赞许表情"）
6. **确定性交互（15s）**：候选人点选 Picker 控件"跳过此题"→ **不经 LLM 直接跳转**（对比语音说"跳过"需经 LLM 解析）
7. **人岗匹配（40s）**：`match_resume_to_jd` → `MatchScoreWidget`，数字人同步口头解读
8. **收尾（30s）**：生成报告 → **布局切到画中画**（数字人缩到右下角）→ `InterviewReportWidget` → 跳转完整报告页
9. **降级（20s）**：刷新/断网 → 自动重连 → 画面不中断
10. 全程右上角**延迟面板**：首字延迟 / 工具耗时 / 打断延迟

| 里程碑 | 内容 | 验收标准 | 前置 |
|---|---|---|---|

| **M3** Function Calling | 11 个工具 + 流式工具循环 + 事件总线 | 能说"我先看下简历"→ 调工具 → 接着讲结论 | M0 |

| **M5** 可观测与容错 | 延迟面板、错误码文案、重连、WebGL 自愈 | 演示视频中可现场展示指标与降级 | M1 |

**关键排序原则**：
- **M2 的 §2.2 前置验证要尽早做**——如果表情在当前部署环境不可用，整个"具身协同"的论证需要调整，越早发现越好。
- **M4 的 W0（类型探测）必须排在通道 B 编码之前**——否则 `proxyWidget` 的 key 全是猜的，写完不生效还找不到原因。
- **M1 的分句与队列是"手感"的地基**——它不影响功能正确性，但直接决定数字人"像不像人在说话"，建议不要跳过。
